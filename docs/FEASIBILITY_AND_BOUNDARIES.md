# 可行性评估与项目边际（2026-05-06）

## 一、可行性结论（结论先行）

项目在“先上线、再扩展”的目标下可行，且当前仓库已经具备可运行 MVP 的核心条件：
- 可运行 Web 站点（页面 + API + 投稿 + 审核基础流）；
- 可执行部署链路（本地守护、Nginx、Render、GitHub Actions）；
- 可执行数据采集起点（Crossref + 受限环境回退机制）；
- 生产数据库目标模型（Postgres schema v1）。

但要达成“稳定运营的公网站点”，仍有 4 个上线门槛未闭环：
1. 生产主库迁移与数据持久化策略；
2. 角色权限与审计日志；
3. 自动推送链路（日报 + 渠道 + 重试）；
4. 多源采集与自动去重评分。

---

## 二、当前能力边界（已经能做）

### 2.1 产品能力
- 浏览：首页、列表、详情、地图（JSON点位）、昨日新增。
- 投稿：前台提交 -> 后台状态更新。
- API：species/media/sources/occurrences/digests/facets/submissions。

### 2.2 工程能力
- CI 已可运行单测和烟测。
- 可通过 Docker/Render 或 systemd/supervisor 上线。
- 具备健康检查脚本和部署手册。

### 2.3 数据能力
- Postgres 生产模型明确。
- SQLite MVP 可快速验证流程。
- Crossref 采集可在代理受限场景下回退离线样本。

---

## 三、关键不可忽视边际（现在不能假装已完成）

### 3.1 数据持久化边际
- Render + 本地 SQLite 在容器重建时可能丢失数据。
- 边际策略：生产切 Postgres，并加每日备份与回滚演练。

### 3.2 合规边际（图片/版权）
- 未经授权的论文图版和社媒图不可默认托管。
- 边际策略：`linked_only` 默认，许可清晰再托管。

### 3.3 自动化边际
- 仅 Crossref 不足以支撑高质量“新种发现”。
- 边际策略：引入 Taiwania/Phytotaxa/命名学核验，多源交叉验证。

### 3.4 运营边际
- 未建立角色权限 + 审核留痕时，不适合多编辑协同。
- 边际策略：先做 RBAC 与审计，再扩大内容团队。

---

## 四、上线可行路径（建议）

### 阶段 A：可公开试运行（1~2 周）
- 切到 Postgres 托管主库。
- 保留 SQLite 仅用于本地开发。
- 完成域名 + HTTPS + 基础监控。

### 阶段 B：可持续运营（2~4 周）
- 上线 RBAC、操作日志。
- 日报任务（按 entered_at + 时区）+ 邮件通道。
- 去重评分规则上线（至少 DOI + 学名 + 标题相似）。

### 阶段 C：可规模增长（4~8 周）
- 接入更多权威源并建立适配器抽象。
- 推送扩展到 Telegram/企业微信。
- 地图升级与多语言字段。

---

## 五、风险矩阵（高优先）

| 风险 | 触发条件 | 影响 | 缓解 |
|---|---|---|---|
| 数据丢失 | 容器重建且只用 SQLite | 高 | Postgres + 每日备份 |
| 图片侵权 | 未授权图默认托管 | 高 | `linked_only` 默认 + 下架流程 |
| 误报/重报 | 单源采集或无去重 | 中高 | 多源核验 + 评分阈值 |
| 推送失效 | 无失败重试队列 | 中 | delivery_logs + retry |
| 后台误操作 | 无审计与权限分级 | 中高 | RBAC + 操作留痕 |

---

## 六、完成定义（DoD，建议执行口径）

满足以下条件才称为“功能齐全版一期上线”：
1. 生产环境使用 Postgres，备份任务已验证。
2. 权限体系可区分管理员/编辑/审核员。
3. 日报任务每日执行并可回溯日志。
4. 采集至少 3 源并有去重评分。
5. 域名 HTTPS 公网可用，健康检查与告警可用。
